# 更新项目规范 - 沉淀可执行的约定

当你在采集、整理、校验、分析或讨论中得到有价值的认知时，用它更新对应的规范文档。

**时机**：完成一个任务后、发现并修正某类错误后、发现新的数据来源或口径后

---

## 规范优先原则（重要）

本项目中「spec」指的是**可执行的约定**，不是空泛的原则：

- 具体的字段名、单位、枚举取值、口径定义
- 可判定的校验标准（什么情况判为不通过）
- 可复现的验证方法（怎么独立重算、怎么做敏感性测试）

若改动涉及**跨来源口径**或**新的校验/验证手段**，规范的深度是强制的。

### 强制触发条件

出现以下任一情况时，必须写足深度：

- 新增/修改字段名、单位或枚举取值
- 新增/修改指标口径或计算方式
- 新增数据来源，或来源口径与既有来源不同
- 新增数据校验维度或判定标准
- 新增结论验证方法
- 出现跨区/跨时点的口径差异

### 强制内容（七段式）

触发上述条件时，规范条目必须包含：

1. 范围 / 触发条件
2. 字段或指标定义（名称、类型、单位、取值集合）
3. 口径契约（来源、时点、计算方式、与其他口径的差异）
4. 校验与失败矩阵（`<条件> -> <判定>`）
5. 好 / 一般 / 差 三类样例
6. 必须执行的校验或验证动作（含判定点）
7. 错误 vs 正确（至少一对）

## 何时更新规范

| 触发 | 示例 | 目标文件 |
|------|------|----------|
| **新增数据来源** | 找到区教育局公示的划片原文 | `spec/data/source-registry.md` + 目录 `来源.md` |
| **新增/修改字段** | 需要记录「是否九年一贯制」 | `spec/data/field-conventions.md` |
| **确立目录/命名约定** | 统一原始文件放 `原始文件/` | `spec/data/directory-structure.md` |
| **做出口径决定** | 单价统一按建筑面积 | `spec/data/field-conventions.md` |
| **发现新的数据陷阱** | 同名不同校导致跨区合并出错 | `spec/quality/data-validation.md` 的「常见真实陷阱」 |
| **新增校验手段** | 用别名映射表检测漏配 | `spec/quality/data-validation.md` |
| **发现分析陷阱** | 挂牌价当成交价导致溢价高估 | `spec/analysis/method-guidelines.md` 反模式 |
| **新增验证手段** | 剔除极端值做稳健性测试 | `spec/analysis/conclusion-verification.md` |
| **新的思考触发器** | 「做时间序列前先确认口径是否变过」 | `spec/guides/*.md` 的检查清单条目 |

**关键认知**：规范更新不只是为了记问题。每一次数据与分析工作都包含口径决定与
判断标准，未来的人与 AI 需要它们才能安全地做下去。

## 规范结构总览

```
.trellis/spec/
├── data/              # 数据规范（目录、命名、来源登记、字段口径）
│   ├── index.md
│   └── *.md
├── quality/           # 数据正确性校验规范
│   ├── index.md
│   └── data-validation.md
├── analysis/          # 分析与结论验证规范
│   ├── index.md
│   ├── method-guidelines.md
│   └── conclusion-verification.md
└── guides/            # 思考清单（不是规范本身）
    ├── index.md
    └── *.md
```

### 规范 vs 指南：分清两者

| 类型 | 位置 | 用途 | 内容风格 |
|------|------|------|----------|
| **规范** | `<layer>/*.md` | 告诉 AI「怎么做才算对」 | 字段定义、口径契约、失败矩阵、样例、判定标准 |
| **指南** | `guides/*.md` | 帮 AI「动手前该想什么」 | 检查清单、提问、指向规范 |

**判断规则**：

- 「这是**怎么做**」→ 放进 `<layer>/`
- 「这是动手前**该考虑什么**」→ 放进 `guides/`

**示例**：

| 认知 | 错误位置 | 正确位置 |
|------|----------|----------|
| 「单价统一按建筑面积口径，来源是使用面积时必须换算」 | ❌ `guides/`（太具体） | ✅ `spec/data/field-conventions.md` |
| 「做时间序列前先确认口径是否变过」 | ❌ 规范文件（太抽象） | ✅ `guides/` 检查清单 |

**指南应是指向规范的短清单**，不要复制规范的详细规则。

## 更新流程

### 第 1 步：明确学到了什么

1. **学到了什么？**（要具体）
2. **为什么重要？**（能挡住什么错误？）
3. **该放哪里？**（哪个规范文件？）

### 第 2 步：给更新分类

| 类型 | 说明 | 动作 |
|------|------|------|
| **口径决定** | 为什么选 A 口径而非 B | 加进对应规范的「口径说明」 |
| **项目约定** | 本项目怎么做 X | 加进对应章节并给示例 |
| **新方法** | 发现的可复用做法 | 加进「方法」章节 |
| **反模式** | 会导致错误的做法 | 加进「反模式 / 不要做」 |
| **常见错误** | 容易犯的错 | 加进「常见陷阱」 |
| **坑（Gotcha）** | 非直观的行为 | 加显著警告 |

### 第 3 步：先读目标规范

编辑前先读现状，以便：

- 理解现有结构
- 避免重复内容
- 找到合适的插入位置

```bash
cat .trellis/spec/<layer>/<file>.md
```

### 第 4 步：执行更新

原则：

1. **具体** —— 给具体示例，不只是抽象规则
2. **说明原因** —— 指出它能防止什么问题
3. **写清契约** —— 字段名、单位、枚举、口径、时点
4. **给正反例** —— 关键约定配「错误 vs 正确」
5. **保持简短** —— 一节讲一个概念

### 第 5 步：按需更新入口

新增章节或状态变化时，更新该层的 `index.md`。

## 更新模板

### 跨来源口径类改动（强制七段式）

```markdown
## 场景：<名称>

### 1. 范围 / 触发
- 触发条件：<为什么需要写足深度>

### 2. 字段 / 指标定义
- 名称、类型、单位、取值集合

### 3. 口径契约
- 来源主体、发布时间、生效时点
- 计算方式
- 与其他口径的差异

### 4. 校验与失败矩阵
- <条件> -> <判定：通过 / 不通过 / 需人工确认>

### 5. 好 / 一般 / 差 样例
- 好：...
- 一般：...
- 差：...

### 6. 必须执行的校验 / 验证动作
- 动作 + 判定点

### 7. 错误 vs 正确
#### 错误
...
#### 正确
...
```

### 追加一条口径决定

```markdown
### 口径决定：[名称]

**背景**：要解决什么问题？

**候选口径**：
1. 口径 A — 简述（可得性、代表性、偏差）
2. 口径 B — 简述

**决定**：选择 X，因为……

**示例**：
（数据片段示例）

**可扩展性**：未来如何扩展或替换该口径
```

### 追加一条项目约定

```markdown
### 约定：[名称]

**是什么**：简述。

**为什么**：本项目为什么这样做。

**示例**：
（数据片段示例）

**相关**：指向相关约定或规范。
```

### 追加一种方法

```markdown
### 方法名称

**问题**：解决什么问题？

**做法**：简述。

**示例**：
```
正确做法
```
```
错误做法
```

**为什么更好**：解释。
```

### 追加一条反模式

```markdown
### 不要：模式名称

**问题**：
```
不要这样做
```

**为什么不好**：说明。

**应当改为**：
```
改为这样做
```
```

### 追加一条常见错误

```markdown
### 常见错误：描述

**症状**：会出什么错

**原因**：为什么会发生

**修正**：如何纠正

**预防**：将来如何避免
```

### 追加一条警告

```markdown
> **警告**：非直观行为的简述。
>
> 什么情况下发生、如何处理。
```

## 交互模式

不确定该更新什么时，回答这些问题：

1. **你刚完成了什么？**
   - [ ] 采集了一批新数据
   - [ ] 修正了数据错误
   - [ ] 完成了分析
   - [ ] 验证了结论
   - [ ] 讨论了做法与口径

2. **你学到或决定了什么？**
   - 口径决定（为什么选 X 而非 Y）
   - 项目约定（本项目怎么做 X）
   - 非直观行为（坑）
   - 更好的做法（方法）

3. **未来的人 / AI 需要知道这个吗？**
   - 为了理解数据含义 → 是，更新规范
   - 为了维护或扩展分析 → 是，更新规范
   - 为了避免重犯 → 是，更新规范
   - 纯一次性细节 → 可以跳过

4. **它属于哪个领域？**
   - [ ] 数据来源与结构（`spec/data/`）
   - [ ] 字段与口径（`spec/data/field-conventions.md`）
   - [ ] 数据正确性校验（`spec/quality/`）
   - [ ] 分析方法（`spec/analysis/method-guidelines.md`）
   - [ ] 结论验证（`spec/analysis/conclusion-verification.md`）
   - [ ] 跨来源一致性（`spec/guides/`）

## 质量检查清单

完成规范更新前：

- [ ] 内容具体、可执行吗？
- [ ] 给了具体示例吗？
- [ ] 解释了 WHY 而不只是 WHAT 吗？
- [ ] 写清了字段/指标定义与口径契约吗？
- [ ] 写了校验与失败矩阵吗？
- [ ] 给了好/一般/差样例吗？
- [ ] 给了错误 vs 正确对照吗？
- [ ] 放在了正确的规范文件里吗？
- [ ] 与既有内容重复了吗？
- [ ] 新加入项目的人能看懂吗？

## 与其他环节的关系

```
工作流程：
  学到东西 → trellis-update-spec → 认知已沉淀
       ↑                                  ↓
  trellis-break-loop ←────────────────── 未来会话受益
  （深度复盘）
```

- `trellis-break-loop` —— 深度复盘，通常会发现需要更新规范
- `trellis-update-spec` —— 实际执行更新
- `trellis:finish-work` —— 提醒你检查规范是否需要更新

## 核心哲学

> **规范是活文档。每一次校正、每一个「原来如此」，都是把判断标准写得更清楚的机会。**

目标是**组织记忆**：

- 一个人学到的东西，所有人受益
- AI 在某个会话学到的，能留存到未来会话
- 错误变成有记录的护栏
