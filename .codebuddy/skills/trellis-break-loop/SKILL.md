# 打破循环 - 深度复盘

当同一类问题被反复修正后，用它做深度分析，打破
「修正 → 忘记 → 重犯」的循环。

---

## 分析框架

从以下 5 个维度复盘刚才修正的问题：

### 1. 根因类别

| 类别 | 特征 | 示例 |
|------|------|------|
| **A. 规范缺失** | 从没写清该怎么做 | 没要求登记来源，于是漏了 |
| **B. 跨来源契约** | 来源之间的口径边界不清 | 假定平台价就是成交价，实际是挂牌价 |
| **C. 变更传播失败** | 改了一处，漏了其他 | 改了字段名，分析文档里的引用没改 |
| **D. 校验覆盖缺口** | 单个检查通过，组合后出错 | 单文件值域合法，关联后出现一对多 |
| **E. 隐式假设** | 依赖未写下的假设 | 假定划片按小区，实际按居委 |

### 2. 此前修正为何失败

若试了多次才对，逐个分析失败原因：

- **表面修正** —— 修了症状，没修根因
- **范围不全** —— 找到根因，但没覆盖所有情况
- **工具局限** —— 搜索没搜到、校验脚本没覆盖该类错误
- **心智模型** —— 一直在同一层找问题，没想到跨来源/跨时点

### 3. 防错机制

| 类型 | 说明 | 示例 |
|------|------|------|
| **文档** | 写下来，让人知道 | 更新思考指南或校验清单 |
| **结构** | 让错误在结构上不可能发生 | 分目录存放不同口径，禁止合并 |
| **入库时校验** | 数据进库前强制检查 | 采集时校验枚举取值与单位 |
| **运行时可观测** | 抽查、对比、告警 | 每次分析前输出样本量与被排除项 |
| **校验覆盖** | 端到端检查 | 校验「关联后」的结果而不只是单文件 |
| **评审清单** | 固定的检查项 | 「来源登记是否更新？」 |

### 4. 系统性扩展

这个问题暴露了什么更大的隐患？

- **同类问题**：还有哪里可能存在同样问题？
- **设计问题**：是不是数据组织方式本身有问题？
- **流程问题**：是不是工作流缺了某一步？
- **认知缺口**：是不是对某类政策/口径的理解有缺？

### 5. 认知沉淀

- [ ] 更新 `.trellis/spec/guides/` 思考指南
- [ ] 更新对应的 `.trellis/spec/` 规范（`data/` / `quality/` / `analysis/`）
- [ ] 若是新陷阱 → 写进 `spec/quality/data-validation.md` 的「常见真实陷阱」
- [ ] 若是分析口径问题 → 写进 `spec/analysis/method-guidelines.md` 的反模式
- [ ] 若是校验盲区 → 写进 `spec/quality/data-validation.md` 的维度或方法

## 核心哲学

> **复盘的价值不在修正了这个错误，而在于让这一类错误不再发生。**

三个层次的认知：

1. **战术**：怎么修好这一个问题
2. **战略**：怎么防止这一类问题
3. **思维**：怎么扩展思考方式

30 分钟的复盘，省下将来 30 小时的重算。

## 思考框架：贝叶斯推理

当多个根因都说得通、证据不完整时，按新证据比例更新你的判断，而不是死守最初假设。

### 第 1 步：建立先验

调查前先写下你相信什么、为什么：

| 假设 | 先验概率 | 理由 |
|------|----------|------|
| H1: [原因 A] | 40% | 这类问题最常见 |
| H2: [原因 B] | 30% | 结合当前来源情况说得通 |
| H3: [其他] | 30% | 兜底 |

先验之和必须为 100%。无法给出概率时，先去调查。

### 第 2 步：观察证据

记录你发现了什么，并说明可靠性：

- 具体观察到了什么？
- 可靠性如何？（原始来源原文 > 平台数据 > 中介口述 > 猜测）
- 是否有多个假设都能解释它？

### 第 3 步：更新判断

对每个假设问：**若该假设成立，出现这个证据的可能性有多大？**

方向比计算更重要：

- 证据被 H1 强烈预测 → H1 概率上升
- 证据与 H2 矛盾 → H2 概率下降
- 证据在所有假设下同样可能出现 → 不更新

### 第 4 步：寻找区分性证据

不要收集更多同类证据。找**在主要假设之间差异明显**的证据。

> 若 H1 与 H3 接近：「如果 H1 成立而 H3 不成立，我会看到什么？」然后去查。

### 第 5 步：声明置信度

| 置信度 | 动作 |
|--------|------|
| 90%+ | 按此结论推进，持续观察 |
| 70-90% | 推进，同时加一条反向检查 |
| 50-70% | 先验证假设再定论 |
| <50% | 证据不足，不要猜 |

证据不完整时不要表达二元确定性。使用「最可能」「看似合理但可能性不大」「值得进一步核查」。

### 常见谬误

| 谬误 | 示例 | 纠正 |
|------|------|------|
| **忽略基础概率** | 「校验失败 → 数据一定错了」 | 校验失败还有多少其他原因？ |
| **确认偏误** | 「肯定是口径问题，去找口径证据」 | 主动找**反对**你首要假设的证据 |
| **锚定** | 「上次是时点问题，这次大概也是」 | 先验来自当前上下文，而不是上一次的问题 |

## 复盘后的立即动作

**重要**：完成上述分析后，必须立即：

1. **更新规范 / 指南** —— 不要只列 TODO，实际去改文件：
   - 跨来源/跨时点问题 → 更新 `spec/guides/data-consistency-thinking-guide.md`
   - 复用与可追溯问题 → 更新 `spec/guides/reuse-and-traceability-thinking-guide.md`
   - 数据陷阱 → 更新 `spec/quality/data-validation.md`
   - 分析口径问题 → 更新 `spec/analysis/method-guidelines.md`
   - 验证盲区 → 更新 `spec/analysis/conclusion-verification.md`
   - 数据组织问题 → 更新 `spec/data/directory-structure.md` 或 `field-conventions.md`

2. **提交规范更新** —— 规范更新是主要产出，不只是分析文字

> **留在对话里的复盘没有价值。价值在被更新的规范里。**
